## 1. 联机模式设计

### 1.1 模式选型

| 模式 | 描述 | 技术复杂度 | 体验价值 | 决策 |
|------|------|-----------|---------|------|
| **Co-op Run** | 2 人共享一局 run，各自牌组，共享敌人与地图 | 中 | 高——合作 deckbuilder 几乎没有先例 | **采纳** |
| Versus Run | 2 人各自独立 run，比谁先通关 / 分数高 | 低 | 中——本质是异步竞速 | 后续考虑 |
| 每日挑战排行 | 所有人用相同 seed，比分数 | 低 | 中——已有架构天然支持 | 后续考虑 |
| 观战模式 | 第 3 人观看他人 run | 低 | 低 | 不做 |

### 1.2 Co-op Run 核心设计

```
┌──────────────────────────────────────────────────────┐
│                   Co-op Run 概念                      │
│                                                      │
│  2 名玩家 · 共享地图 · 各自牌组 · 共享敌人 · 共享战利品  │
│                                                      │
│  玩家 A (Host)        玩家 B (Client)                 │
│  ├─ 自己的牌组         ├─ 自己的牌组                    │
│  ├─ 自己的手牌         ├─ 自己的手牌                    │
│  ├─ 自己的能量         ├─ 自己的能量                    │
│  ├─ 自己的 HP          ├─ 自己的 HP                     │
│  └─ 共享: 敌人 / 地图 / 金币 / 遗物 / 战利品选择        │
│                                                      │
│  任一玩家 HP 归零 → run 失败                           │
│  所有敌人死亡 → 战斗胜利                               │
└──────────────────────────────────────────────────────┘
```

**关键设计决策**：

| 维度 | 选择 | 理由 |
|------|------|------|
| 回合结构 | **同步玩家回合** | 两人同时出牌，不等对方 → 节奏快，不卡顿 |
| 能量 | **各自独立** (各 3 点) | 每人独立决策，不抢资源 |
| 牌组 | **各自独立** | 构筑身份感，各有所长 |
| 手牌可见性 | **互相可见** | Co-op 核心是协作，信息共享促进策略讨论 |
| 敌人 | **共享** | 共同敌人 = 共同目标 |
| 敌人目标选择 | **AI 决定** | 按仇恨值/HP/随机选择攻击对象 |
| 战利品 | **共享选择** | 卡牌奖励两人各选一张，遗物轮流选 |
| 路径选择 | **Host 决定** | Host 选路，Client 可标记建议 |

## 2. 架构决策记录 (ADR 补充)

### ADR-006: Host 权威游戏逻辑 (多人模式)

**Status**: Accepted

**Context**: 单人模式采用客户端权威（ADR-001）。多人模式需要双方状态一致。选项：(A) C# 服务端权威——需将全部游戏逻辑移植到 C#；(B) Godot Host 权威——Host 运行游戏逻辑，Client 发送命令；(C) P2P 无权威——双方各自运行逻辑并同步——竞态风险高。

**Decision**: 多人模式采用 Godot Host 权威。Host 玩家的 Godot 实例运行完整游戏逻辑（EffectResolver、DeckManager、EnemyAI 等），Client 玩家的 Godot 实例退化为瘦客户端（只渲染 + 发送命令）。C# 服务端角色不变——仍负责匹配、验证、元进度。

**Consequences**:
- 更容易：复用现有全部游戏逻辑代码，无需移植到 C#；Godot MultiplayerAPI 天然支持 Host-Client 拓扑
- 更难：Host 断线 = 游戏中断（需要状态快照 + 迁移机制）；Host 可能作弊（通过命令日志 + 服务端验证缓解）
- 关键约束：单人与多人共享同一套 `game/` 逻辑层，通过 `is_multiplayer_authority()` 守卫切换行为

---

### ADR-007: 快照同步 + RPC 混合通信

**Status**: Accepted

**Context**: Godot 提供两种同步机制：MultiplayerSynchronizer（属性级自动同步）和 RPC（显式函数调用）。杀戮尖塔的战斗状态是复杂的嵌套结构（手牌数组、buff 字典、敌人列表），MultiplayerSynchronizer 难以直接同步自定义对象。

**Decision**: 采用混合策略——
- **MultiplayerSynchronizer**：同步标量状态（HP、能量、格挡、回合数、阶段）到 PlayerEntity 和 EnemyEntity
- **RPC 快照**：每次状态变更后，Host 广播完整战斗状态快照（Dictionary），Client 覆盖应用
- **RPC 命令**：Client → Host 的玩家操作（出牌、结束回合、选路径）

**Consequences**:
- 更容易：快照是幂等的（重复应用不会出错），调试简单（打印快照即可对比状态），天然支持断线重连（重连后发一次快照即可同步）
- 更难：快照带宽比增量同步大（但回合制游戏频率低，可接受）；需要设计快照的序列化/反序列化

---

### ADR-008: C# 服务端可选中继模式

**Status**: Accepted

**Context**: Host-Client 直连 ENet 需要 Host 开放端口（NAT 穿透问题）。部分玩家在严格 NAT 后无法直连。

**Decision**: C# 服务端提供可选的中继模式。当 Client 无法直连 Host 时，通过 C# 服务端转发 ENet 数据包。中继模式仅转发，不解析游戏逻辑。

**Consequences**:
- 更容易：解决 NAT 穿透问题，所有网络环境可联机
- 更难：中继模式增加延迟（多一跳）；中继模式增加服务端负载（带宽 × 房间数）
- 备选方案：WebRTC + STUN/TURN（更适合浏览器导出，但实现更复杂）

## 3. 网络拓扑

### 3.1 三方架构

```
Player A (Host, peer_id=1)          C# Server (.NET 8)          Player B (Client, peer_id=2)
┌────────────────────────┐       ┌──────────────────┐        ┌────────────────────────┐
│  Godot                 │       │                  │        │  Godot                 │
│  ┌──────────────────┐  │ REST  │  Matchmaking     │ REST   │  ┌──────────────────┐  │
│  │ Game logic       │◄─┼──────►│  Lobby (SignalR) │◄──────►│  │ Thin client      │  │
│  │ (AUTHORITY)      │  │       │  Validation      │        │  │ (renderer only)  │  │
│  │                  │  │       │  Meta-Prog       │        │  │                  │  │
│  │ EffectResolver   │  │       │  Relay (opt)     │        │  │ StateReceiver    │  │
│  │ DeckManager      │  │       │                  │        │  │ CommandSender    │  │
│  │ EnemyAI          │  │       │  PostgreSQL      │        │  │ AnimationPlayer  │  │
│  │ MapGenerator     │  │       │  Redis           │        │  │ LocalInput       │  │
│  └──────────────────┘  │       └──────────────────┘        │  └──────────────────┘  │
│         │              │               │                   │         │              │
│  ┌──────▼──────┐       │               │                   │  ┌──────▼──────┐       │
│  │ ENet server │◄──────┼───────────────┼───────────────────┼─►│ ENet client │       │
│  │ port 7777   │       │   ENet (game state + RPC)         │  │             │       │
│  └─────────────┘       │                                   │  └─────────────┘       │
└────────────────────────┘                                   └────────────────────────┘
```

### 3.2 通信通道

| 通道 | 协议 | 用途 | 频率 | 延迟敏感 |
|------|------|------|------|---------|
| **ENet (Host ↔ Client)** | UDP | 游戏状态快照、RPC 命令、战斗事件 | 每次状态变更（秒级） | 中——回合制容忍 200ms |
| **SignalR (Both ↔ Server)** | WebSocket | 大厅实时通知、房间状态推送 | 事件驱动 | 低 |
| **REST (Both ↔ Server)** | HTTPS | 认证、存档、元进度、排行榜 | 偶发 | 低 |

### 3.3 为什么不是 C# 服务端权威？

| 对比项 | C# 服务端权威 | Godot Host 权威 (采纳) |
|--------|-------------|----------------------|
| 游戏逻辑实现 | 需将全部 GDScript 逻辑移植到 C# | **零移植**——复用现有 `game/` 层 |
| 开发成本 | 高——双端逻辑维护 | 低——Host 复用单人模式逻辑 |
| 延迟 | Client → Server → Client (2 跳) | Client → Host (1 跳) |
| NAT 穿透 | 不需要（Client 直连 Server） | 需要（直连或中继） |
| Host 断线 | 不影响（Server 持续运行） | **需要迁移机制** |
| 作弊防护 | 强（Server 全权） | 中（Host 可作弊，靠验证缓解） |

**最终判断**：对于 Co-op PvE 游戏，Host 权威的开发成本优势和延迟优势 outweigh 作弊风险。Host 断线通过状态快照 + Host 迁移解决。

## 4. 权威模型迁移

### 4.1 单人 vs 多人权威对比

```
单人模式 (ADR-001):
  Client = 权威 (运行全部游戏逻辑)
  Server = 验证者 (事后重放验证)

多人模式 (ADR-006):
  Host Client = 权威 (运行全部游戏逻辑)
  Guest Client = 瘦客户端 (渲染 + 发命令)
  Server = 匹配 + 验证 (不变)
```

### 4.2 is_multiplayer_authority() 守卫

核心改造：所有状态变更入口添加权威检查。

```gdscript
# game/combat/EffectResolver.gd — 改造后

func process_command(cmd: PlayCardCommand) -> void:
    # 多人模式下，只有 Host (权威) 执行游戏逻辑
    if multiplayer.has_multiplayer_peer() and not is_multiplayer_authority():
        # Client 不执行逻辑，只发送命令到 Host
        request_play_card.rpc_id(1, cmd.card.instance_id, cmd.target_index)
        return
    
    # 以下只有 Host 执行（单人模式下 is_multiplayer_authority() 返回 true）
    if not CardValidator.validate(cmd, combat_state):
        return
    
    combat_state.energy -= cmd.card.cost
    
    for effect in cmd.card.effects:
        effect_queue.push(effect)
    
    while not effect_queue.is_empty():
        var effect = effect_queue.pop()
        var result = _resolve_effect(effect)
        event_bus.emit_signal("effect_resolved", result)
    
    if cmd.card.has_tag("EXHAUST"):
        combat_state.exhaust_pile.append(cmd.card)
    else:
        combat_state.discard_pile.append(cmd.card)
    
    # 多人模式：广播状态快照
    if multiplayer.has_multiplayer_peer() and is_multiplayer_authority():
        _broadcast_combat_state()
    
    # 记录命令日志（单人/多人都需要，用于验证）
    command_log.append(cmd)
```

**关键原则**：`game/` 层代码不判断"是否多人"，只判断"是否权威"。单人模式下 `is_multiplayer_authority()` 始终返回 `true`（无 multiplayer peer 时）。多人模式下只有 Host 返回 `true`。

### 4.3 权威设置

```gdscript
# autoload/GameManager.gd — 多人模式初始化

func start_multiplayer_as_host() -> void:
    var peer := ENetMultiplayerPeer.new()
    peer.create_server(PORT, MAX_CLIENTS)
    multiplayer.multiplayer_peer = peer
    multiplayer.peer_connected.connect(_on_peer_connected)
    multiplayer.peer_disconnected.connect(_on_peer_disconnected)
    # Host 的 peer_id = 1，自动是所有节点的权威

func join_multiplayer_as_client(host_address: String) -> void:
    var peer := ENetMultiplayerPeer.new()
    peer.create_client(host_address, PORT)
    multiplayer.multiplayer_peer = peer
    multiplayer.server_disconnected.connect(_on_host_disconnected)
    # Client 的 peer_id 由 Host 分配，非 1

func _on_peer_connected(peer_id: int) -> void:
    # Host: 新玩家加入，为其创建 PlayerEntity
    _spawn_player_entity(peer_id)

func _on_host_disconnected() -> void:
    # Client: Host 断线，尝试迁移或返回大厅
    _handle_host_migration()
```

## 6. Co-op 战斗设计

### 6.1 同步回合制

**核心设计**：两名玩家共享同一个"玩家回合"，可以同时出牌，不需要等对方。只有当两人都点击"结束回合"后，才进入敌人回合。

```
回合流程:
  1. SyncDrawPhase (Host 执行)
     - Host 为 Player A 抽 5 张
     - Host 为 Player B 抽 5 张
     - 各自补充能量
     - 广播状态快照

  2. PlayerActionPhase (异步，两人同时)
     - Player A 可随时出牌 → request_play_card → Host 验证+执行 → 广播
     - Player B 可随时出牌 → request_play_card → Host 验证+执行 → 广播
     - Player A 点击结束 → request_end_turn(A)
     - Player B 点击结束 → request_end_turn(B)

  3. WaitForBothEnd (Host 等待)
     - A_ended && B_ended → 进入敌人回合
     - 如果只有一方结束，另一方仍可出牌

  4. EnemyTurnPhase (Host 执行)
     - IntentPhase: 敌人计算意图 + 选择目标 (Player A or B)
     - EnemyActionPhase: 按速度顺序执行攻击
     - ResolvePhase: buff/debuff 结算 + 胜负检查
     - 广播敌人行动结果

  → 回到步骤 1 (下一回合)
```

### 6.2 敌人目标选择 AI

```gdscript
# game/combat/EnemyAI.gd — Co-op 扩展

func calculate_target(rng: RandomNumberGenerator, 
                      players: Array[PlayerState]) -> int:
    # 返回目标玩家的 index (0 = Player A, 1 = Player B)
    
    # 策略 1: 仇恨值系统 — 攻击仇恨最高的玩家
    var highest_threat := -1
    var target := 0
    for i in players.size():
        if players[i].threat > highest_threat:
            highest_threat = players[i].threat
            target = i
    
    # 策略 2: 概率修正 — HP 低的玩家有更高被攻击概率
    var low_hp_player = _find_lowest_hp_player(players)
    if rng.randf() < 0.3:  # 30% 概率攻击低血量玩家
        target = low_hp_player
    
    # 策略 3: 随机 — 10% 概率完全随机
    if rng.randf() < 0.1:
        target = rng.randi() % players.size()
    
    return target

func _find_lowest_hp_player(players: Array[PlayerState]) -> int:
    var min_hp := 999999
    var idx := 0
    for i in players.size():
        if players[i].hp < min_hp:
            min_hp = players[i].hp
            idx = i
    return idx
```

static func apply(snapshot: Dictionary, combat_state: CombatState) -> void:
    combat_state.turn = snapshot.turn
    combat_state.phase = snapshot.phase
    
    for i in snapshot.players.size():

    combat_state.enemies.clear()
    for e in snapshot.enemies:
        var enemy := EnemyState.new()
        enemy.def_id = e.def_id
        enemy.hp = e.hp
        enemy.max_hp = e.max_hp
        enemy.block = e.block
        enemy.buffs = e.buffs.duplicate()
        enemy.intent_type = e.intent_type
        enemy.intent_value = e.intent_value

## 9. 断线与重连

### 9.1 断线场景分析

| 场景 | 影响 | 处理策略 |
|------|------|---------|
| **Client 断线** | Client 掉线，Host 持续运行 | Host 暂停战斗，等待 Client 重连（60s 超时） |
| **Host 断线** | 游戏中断，Client 失去权威 | Client 上报 C# 服务端 → 服务端触发 Host 迁移 |
| **C# 服务端断线** | 匹配/验证不可用，但游戏可继续 | 游戏继续，存档暂存本地，服务端恢复后同步 |
| **双方同时断线** | Run 中断 | C# 服务端保存最后检查点，支持恢复 |

### 9.2 Client 断线重连

```gdscript
# scripts/autoload/GameManager.gd

const RECONNECT_TIMEOUT := 60.0  # 秒

var _reconnect_timer: float = 0.0
var _disconnected_peer_id: int = -1

func _on_peer_disconnected(peer_id: int) -> void:
    if not multiplayer.is_server():
        return  # 只有 Host 处理
    
    _disconnected_peer_id = peer_id
    _reconnect_timer = RECONNECT_TIMEOUT
    
    # 暂停战斗（不结束，等重连）
    turn_manager.set_paused(true, "等待玩家重连...")
    
    # 通知 C# 服务端
    NetworkClient.post("/api/lobby/%s/player_disconnected" % _lobby_id, {
        "peer_id": peer_id
    })

func _process(delta: float) -> void:
    if _disconnected_peer_id > 0:
        _reconnect_timer -= delta
        if _reconnect_timer <= 0:
            _on_reconnect_timeout()

func _on_reconnect_timeout() -> void:
    # 超时：Client 视为放弃，Host 可选择继续单人或结束
    turn_manager.set_paused(false)
    _disconnected_peer_id = -1
    # 通知 UI: 玩家 B 已断线，继续单人模式或结束 run

func _on_peer_connected(peer_id: int) -> void:
    if multiplayer.is_server() and peer_id == _disconnected_peer_id:
        # Client 重连成功
        _disconnected_peer_id = -1
        turn_manager.set_paused(false)
        # 发送完整状态快照进行重同步
        _broadcast_full_state()
```

## 10. 安全考量

### 10.1 威胁模型

| 威胁 | 风险等级 | 缓解措施 |
|------|---------|---------|
| Client 伪造出牌（不存在的卡牌） | 高 | Host 验证卡牌 instance_id 在玩家手牌中 |
| Client 伪造他人操作 | 高 | `get_remote_sender_id()` 验证身份匹配 |
| Client 篡改能量/HP | 中 | 这些值由 Host 维护，Client 只接收快照 |
| Host 恶意作弊 | 低 | Run 结束后 C# 服务端重放命令日志验证 |
| 中间人攻击 | 中 | ENet 可配置加密；REST 已用 HTTPS |
| 大厅注入攻击 | 中 | C# 服务端验证所有大厅操作，JWT 认证 |

### 10.2 Host 权威安全模式

```gdscript

    var sender_id := multiplayer.get_remote_sender_id()
    
    # 3. 验证发送者身份
    if not _is_valid_sender(sender_id, params):
        return  # 静默拒绝
    
    # 4. 验证操作合法性
    if not _is_valid_action(params):
        return  # 静默拒绝
    
    # 5. 执行 + 广播
    _do_action(params)
    _broadcast_state()
```

### 10.3 Run 结束后验证

```csharp
// STS.Server.Application/Services/ValidationService.cs — Co-op 扩展

public ValidationResult ValidateCoopRun(Run run, List<int> participantPeerIds)
{
    // 1. 验证所有命令的 sender_id 都在参与者列表中
    foreach (var cmd in run.CommandLog)
    {
        if (!participantPeerIds.Contains(cmd.SenderPeerId))
            return ValidationResult.Fail($"Unknown sender: {cmd.SenderPeerId}");
    }
    
    // 2. 验证命令顺序合理性（不能在敌人回合出牌）
    if (!ValidateCommandOrdering(run.CommandLog))
        return ValidationResult.Fail("Invalid command ordering");
    
    // 3. 验证 HP 一致性（两名玩家的 HP 都在合法范围内）
    if (!ValidatePlayerHP(run))
        return ValidationResult.Fail("HP out of bounds");
    
    // 4. 验证牌组构成（两人各自的牌组合法）
    foreach (var peerId in participantPeerIds)
    {
        if (!ValidateDeckComposition(run, peerId))
            return ValidationResult.Fail($"Invalid deck for peer {peerId}");
    }
    
    return ValidationResult.Ok();
}
```

## 12. 设计检查清单

### 12.1 权威与安全

- [ ] 所有 `@rpc("any_peer")` 函数有 `multiplayer.is_server()` 守卫
- [ ] 所有 `@rpc("any_peer")` 函数调用 `get_remote_sender_id()` 验证发送者
- [ ] 所有状态变更有 `is_multiplayer_authority()` 检查
- [ ] Client 永远不直接修改 `CombatState`（只通过 RPC 请求 Host）
- [ ] `MultiplayerSynchronizer` 只同步标量属性，不同步复杂结构
- [ ] `MultiplayerSpawner` 注册了所有需要网络生成的场景
- [ ] 所有网络化节点在 `add_child` 后立即 `set_multiplayer_authority(1)`

### 12.2 状态同步

- [ ] Host 每次状态变更后广播快照
- [ ] 快照包含完整可重建状态（手牌、敌人、buff、牌堆计数）
- [ ] Client 收到快照后幂等应用（重复应用不出错）
- [ ] `MultiplayerSynchronizer` 和快照不同步同一属性
- [ ] 快照大小 < 5 KB（回合制可接受）
- [ ] 战斗开始时发送完整初始化快照

### 12.3 断线处理

- [ ] Client 断线时 Host 暂停战斗并等待重连
- [ ] 重连超时（60s）后 Host 可继续单人或结束
- [ ] Client 重连后 Host 发送完整状态快照
- [ ] Host 断线时 Client 通知 C# 服务端
- [ ] Host 迁移后状态从最后检查点恢复
- [ ] 紧急存档在断线时立即保存到本地

### 12.4 Co-op 战斗

- [ ] 两名玩家可同时出牌（无阻塞）
- [ ] 敌人回合只在双方都结束后开始
- [ ] 敌人意图显示攻击目标（Player A or B）
- [ ] 任一玩家 HP 归零 → run 失败
- [ ] 卡牌奖励各选一张
- [ ] 遗物轮流选择
- [ ] 金币共享池
- [ ] 路径选择由 Host 执行，Client 可标记建议
