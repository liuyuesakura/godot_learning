## 1. 架构概述

### 1.1 设计目标

| 目标 | 衡量标准 | 优先级 |
|------|---------|--------|
| **单局零延迟响应** | 出牌到效果反馈 < 16ms（1帧） | P0 |
| **离线可玩** | 无网络时完整可玩一局 | P0 |
| **运行可验证** | 服务端可独立验证 run 完整性 | P1 |
| **内容热更新** | 新增卡牌/敌人/遗物无需重新编译 | P1 |
| **多人扩展预留** | 架构不阻碍未来加入合作/对战模式 | P2 |

### 1.2 技术栈选型

| 层 | 技术选型 | 选型理由 |
|----|---------|---------|
| **客户端引擎** | Godot 4.x (GDScript) | 开源免费、节点树天然适配状态机、2D 性能优秀、跨平台导出 |
| **服务端框架** | .NET 8 / ASP.NET Core | 高性能、强类型、EF Core 生态成熟、跨平台部署 |
| **数据库** | PostgreSQL | JSONB 支持存档结构化存储、事务可靠、成熟稳定 |
| **缓存** | Redis | 会话管理、排行榜、每日挑战 seed 分发 |
| **通信协议** | REST (HTTPS) | 回合制游戏无需实时通信，REST 足够且调试友好 |
| **内容格式** | JSON + JSON Schema | 双端可读、版本可控、Godot 原生解析 |

### 1.3 架构风格：客户端权威 + 服务端验证

```
┌─────────────────────────────────────────────────────────────┐
│                    核心架构决策                               │
│                                                             │
│  游戏逻辑运行在客户端 → 零延迟、可离线                        │
│  服务端持有 source of truth → 存档、验证、元进度              │
│  双端共享内容定义 → 数据驱动，单一来源                        │
└─────────────────────────────────────────────────────────────┘
```

**为什么不是服务端权威？**

杀戮尖塔是回合制单机 roguelike，没有 PvP 竞争场景。服务端权威会引入：
- 每次出牌的网络往返延迟（破坏手感）
- 离线不可玩（违反 roguelike "随时随地一局"的体验目标）
- 服务端需要完整复刻游戏逻辑（开发成本翻倍）

**客户端权威的代价**：作弊风险。但对于 PvE roguelike，作弊只影响自己的体验和排行榜公信力。通过命令日志 + 服务端重放验证，可以在不牺牲手感的前提下控制作弊影响面。

## 2. 架构决策记录 (ADR)

### ADR-001: 客户端权威游戏逻辑 + 服务端验证

**Status**: Accepted

**Context**: 杀戮尖塔是回合制单机 roguelike，核心体验是"随时随地开一局"。需要零延迟的出牌反馈和离线可玩性。同时需要服务端存档同步和排行榜公信力。

**Decision**: 游戏逻辑（战斗、抽牌、地图生成、效果结算）全部在客户端运行。服务端不运行游戏逻辑，而是通过命令日志重放来验证 run 合法性。

**Consequences**:
- 更容易：出牌零延迟、离线可玩、客户端开发独立于服务端
- 更难：需要在客户端实现命令日志记录、服务端需要独立实现验证逻辑（非完整重放，而是关键节点校验）

---

### ADR-002: 数据驱动内容架构

**Status**: Accepted

**Context**: 卡牌（75+张）、敌人（100+种）、遗物（150+个）、事件（30+种）需要频繁迭代。硬编码在脚本中会导致每次修改都需重新编译和部署。

**Decision**: 所有游戏内容定义为 JSON 数据文件，客户端和服务端从同一数据源加载。使用 JSON Schema 做格式校验。

**Consequences**:
- 更容易：内容迭代无需编译、策划可独立修改、双端数据一致
- 更难：需要构建内容校验管道、运行时类型安全需额外处理

---

### ADR-003: 种子化确定性生成

**Status**: Accepted

**Context**: 地图生成、卡牌奖励、敌人遭遇、抽牌顺序都涉及随机。服务端验证需要能复现客户端的随机结果。

**Decision**: 所有 RNG 调用通过统一的 `RNGManager`，使用 seed 初始化。run 开始时生成一个 master seed，各子系统通过 master seed + 上下文派生子 seed。

**Consequences**:
- 更容易：服务端可复现验证、每日挑战天然支持、录像回放可行
- 更难：开发者不能随意使用 `randi()`，必须通过受管 RNG

---

### ADR-004: 命令模式状态变更

**Status**: Accepted

**Context**: 游戏状态（手牌、牌堆、能量、HP、buff）需要可追踪变更历史，用于验证和潜在的录像回放。

**Decision**: 所有玩家行动封装为 Command 对象。游戏状态只能通过 CommandProcessor 变更，每次变更记录到 CommandLog。

**Consequences**:
- 更容易：状态变更可追踪、撤销/回放可行、验证有据可查
- 更难：增加一层间接性、需要严格的命令设计规范

---

### ADR-005: Godot 场景树即状态机

**Status**: Accepted

**Context**: 游戏有多个宏观状态（主菜单、Run 中、战斗中、事件中、商店中、GameOver），需要清晰的状态转换管理。

**Decision**: 利用 Godot 的场景树天然层级——每个宏观状态是一个 Scene，通过 `SceneTree.change_scene_to()` 切换。RunScene 作为容器场景，子场景（Combat/Event/Shop/Campfire）通过 `add_child` / `remove_child` 动态挂载。

**Consequences**:
- 更容易：状态隔离清晰、Godot 原生机制无需额外状态机框架、场景资源管理自动
- 更难：跨场景数据传递需要通过 Autoload 中介

### 3.2 客户端-服务端职责划分

| 职责 | 客户端 | 服务端 | 说明 |
|------|--------|--------|------|
| 战斗逻辑 | ✅ 主导 | ❌ | 出牌、效果结算、敌人 AI 全在客户端 |
| 地图生成 | ✅ 主导 | ❌ | 客户端用 seed 生成，服务端可复现 |
| 抽牌随机 | ✅ 主导 | ❌ | 客户端用 seed 派生子 RNG |
| 玩家账户 | ❌ | ✅ 主导 | 注册、登录、JWT 认证 |
| Run 存档 | 本地缓存 | ✅ 主导 | 客户端本地存，关键节点同步到服务端 |
| 元进度解锁 | ❌ | ✅ 主导 | 解锁状态由服务端管理 |
| 排行榜 | ❌ | ✅ 主导 | 每日挑战排名、历史最佳 |
| 内容定义 | 加载使用 | ✅ 主导 | 服务端是 source of truth，客户端同步 |
| Run 验证 | 记录命令日志 | ✅ 验证 | 服务端重放关键节点校验合法性 |

### 3.3 通信协议

```
认证:     POST /api/auth/login          → JWT token
同步内容:  GET  /api/content/manifest    → 内容版本 + 差异
          GET  /api/content/{type}      → 卡牌/敌人/遗物定义
Run 管理: POST /api/runs/start           → 返回 run_id + seed
          PUT  /api/runs/{id}/checkpoint → 上传存档检查点
          POST /api/runs/{id}/finish     → 结算 + 验证
元进度:   GET  /api/progression          → 解锁状态
          POST /api/progression/unlock   → 解锁新内容
排行榜:   GET  /api/leaderboard/daily    → 每日挑战排名
```

## 4. 客户端架构 (Godot)

### 4.1 Autoload 单例层

Autoload 是 Godot 的全局单例机制，在整个场景树生命周期内持续存在。

```gdscript
# project.godot 配置
[autoload]
GameManager="*res://autoload/GameManager.gd"
ContentRegistry="*res://autoload/ContentRegistry.gd"
SaveManager="*res://autoload/SaveManager.gd"
NetworkClient="*res://autoload/NetworkClient.gd"
RNGManager="*res://autoload/RNGManager.gd"
```

| Autoload | 职责 | 持有状态 |
|----------|------|---------|
| `GameManager` | 全局状态机入口，管理宏观状态转换 | 当前游戏状态 (MENU / IN_RUN / COMBAT / EVENT...) |
| `ContentRegistry` | 加载和缓存所有内容定义 | 卡牌字典、敌人字典、遗物字典、事件字典 |
| `SaveManager` | 本地存档读写 + 云同步队列 | 当前 run 存档、设置 |
| `NetworkClient` | HTTP API 调用、JWT 管理、请求重试 | 认证 token、请求队列 |
| `RNGManager` | 种子化随机数管理 | master seed、各子系统子 seed |

### 4.4 关键设计：逻辑层与表现层分离

```gdscript
# game/combat/EffectResolver.gd — 纯逻辑，不知道 UI 存在
class_name EffectResolver

var combat_state: CombatState
var effect_queue: Array[CardEffect]
var event_bus: EventBus

func process_command(cmd: PlayCardCommand) -> void:
    if not CardValidator.validate(cmd, combat_state):
        return
    
    # 扣除能量
    combat_state.energy -= cmd.card.cost
    
    # 将卡牌效果加入队列
    for effect in cmd.card.effects:
        effect_queue.push(effect)
    
    # 逐个执行
    while not effect_queue.is_empty():
        var effect = effect_queue.pop()
        var result = _resolve_effect(effect)
        event_bus.emit_signal("effect_resolved", result)
    
    # 卡牌进入弃牌堆（或消耗堆）
    if cmd.card.has_tag("EXHAUST"):
        combat_state.exhaust_pile.append(cmd.card)
    else:
        combat_state.discard_pile.append(cmd.card)
```

```gdscript
# ui/scenes/CombatScene.gd — 表现层，监听逻辑层事件
extends Scene

@onready var effect_resolver: EffectResolver = $EffectResolver

func _ready():
    effect_resolver.event_bus.connect("effect_resolved", _on_effect_resolved)

func _on_effect_resolved(result: EffectResult):
    # 纯视觉表现：播放动画、飘字、粒子
    match result.type:
        EffectResult.Type.DAMAGE:
            DamageNumber.show(result.target, result.value)
            result.target.play_hit_animation()
        EffectResult.Type.BLOCK:
            result.target.show_block_shield(result.value)
```

**核心原则**：`game/` 目录下的代码不 import 任何 UI 节点。`ui/` 目录下的代码可以引用 `game/` 的逻辑类。这使得未来可以：
- 独立测试游戏逻辑（不启动 Godot 场景）
- 替换 UI 层（如从 2D 切到 3D）
- 将逻辑层迁移到 C# 共享库（如果未来需要服务端完整重放）

### 5.3 Run 验证服务

```csharp
// Application/Services/ValidationService.cs
public class ValidationService
{
    private readonly IContentRepository _contentRepo;
    
    /// <summary>
    /// 验证 run 的合法性：重放命令日志，校验关键节点
    /// </summary>
    public ValidationResult Validate(Run run)
    {
        // 1. 用 seed 重新生成地图，校验地图结构一致
        var expectedMap = MapGenerator.Generate(run.Seed, run.CharacterId);
        if (!ValidateMapStructure(expectedMap, run.RunState.Map))
            return ValidationResult.Fail("Map structure mismatch");
        
        // 2. 校验卡牌奖励一致性（seed → 奖励池 → 玩家选择）
        foreach (var combat in run.RunState.CombatHistory)
        {
            var expectedRewards = RewardGenerator.Generate(
                run.Seed, combat.Floor, combat.EnemyType);
            if (!ValidateRewardSelection(expectedRewards, combat.ChosenReward))
                return ValidationResult.Fail($"Invalid reward at floor {combat.Floor}");
        }
        
        // 3. 校验 HP 非负且未超过最大值
        if (run.RunState.CurrentHP < 0 || run.RunState.CurrentHP > run.RunState.MaxHP)
            return ValidationResult.Fail("HP out of bounds");
        
        // 4. 校验牌组构成合法性（所有卡牌 ID 存在于内容定义中）
        foreach (var card in run.RunState.Deck)
        {
            if (!_contentRepo.CardExists(card.Id))
                return ValidationResult.Fail($"Unknown card: {card.Id}");
        }
        
        return ValidationResult.Ok();
    }
}
```

```gdscript
class_name DeckManager

var draw_pile: Array[CardInstance] = []
var hand: Array[CardInstance] = []
var discard_pile: Array[CardInstance] = []
var exhaust_pile: Array[CardInstance] = []

var rng: RandomNumberGenerator  # 从 RNGManager 派生

func shuffle() -> void:
    draw_pile.shuffle()  # Godot 内置洗牌（使用受管 RNG）

func draw(count: int) -> Array[CardInstance]:
    var drawn = []
    for i in count:
        if draw_pile.is_empty():
            _reshuffle_discard()
        if draw_pile.is_empty():
            break  # 牌堆已空
        var card = draw_pile.pop_back()
        hand.append(card)
        drawn.append(card)
    return drawn

func _reshuffle_discard() -> void:
    draw_pile = discard_pile.duplicate()
    discard_pile.clear()
    shuffle()

func discard_card(card: CardInstance) -> void:
    hand.erase(card)
    discard_pile.append(card)

func exhaust_card(card: CardInstance) -> void:
    hand.erase(card)
    exhaust_pile.append(card)

func retain_card(card: CardInstance) -> void:
    # Retain 牌不弃牌，留在手牌
    pass  # 在 EndTurnPhase 中跳过
```

### 7.3 地图系统

#### 7.3.1 地图生成器

```gdscript
# game/map/MapGenerator.gd
class_name MapGenerator

const ACT_COUNT = 3
const FLOORS_PER_ACT = 15
const BOSS_FLOOR_OFFSET = 1  # 第 16 层是 Boss
const PATHS_PER_FLOOR = 4

static func generate(master_seed: int, character_id: int) -> MapData:
    var rng = RandomNumberGenerator.new()
    rng.seed = master_seed
    
    var map = MapData.new()
    
    for act in ACT_COUNT:
        var act_data = _generate_act(rng, act)
        map.acts.append(act_data)
    
    return map

static func _generate_act(rng: RandomNumberGenerator, act: int) -> ActData:
    var act_data = ActData.new()
    act_data.act_index = act
    
    # 生成 15 层节点
    for floor in FLOORS_PER_ACT:
        var row = _generate_floor_row(rng, act, floor)
        act_data.floors.append(row)
    
    # 生成 Boss 层
    act_data.boss = _pick_boss(rng, act)
    
    # 生成路径连接
    _generate_paths(rng, act_data)
    
    return act_data

static func _generate_floor_row(rng: RandomNodeGenerator, act: int, floor: int) -> FloorRow:
    var row = FloorRow.new()
    row.floor = floor
    
    # 节点类型概率表（按 Act 调整）
    var node_weights = _get_node_weights(act, floor)
    
    for col in PATHS_PER_FLOOR:
        var node_type = _weighted_pick(rng, node_weights)
        row.nodes.append(MapNode.new(floor, col, node_type))
    
    return row
```

```
  │    │    ├── CardValidator.validate() → 能量够吗？目标合法吗？
  │    │    ├── EffectResolver.enqueue(effects)
  │    │    ├── EffectResolver.process_queue()
  │    │    │    └── 逐个执行 → EventBus.emit("effect_resolved")
  │    │    ├── DeckManager.discard_card() / exhaust_card()
  │    │    └── CommandLog.append(PlayCardCommand)
  │    │
  │    └── UI 层接收事件 → 播放动画、飘字、粒子
  │
  ├──  玩家点击"结束回合"
  │    ├── CommandProcessor.process(EndTurnCommand)
  │    ├── 弃手牌（Retain 除外）
  │    ├── 清零能量
  │    └── 切换到 ENEMY_TURN
  │
  ▼
敌人回合
  │
  ├──  IntentPhase: 每个敌人计算下回合意图
  │    └── EnemyAI.calculate_intent(seed, turn)
  │
  ├──  EnemyActionPhase: 按速度顺序执行
  │    ├── 对每个敌人:
  │    │    ├── 读取当前意图
  │    │    ├── 执行行动（攻击/格挡/施法）
  │    │    └── EffectResolver 处理效果
  │    └── UI 层播放敌人行动动画
  │
  └──  ResolvePhase: 结算 buff、检查胜负
       ├── 如果玩家 HP <= 0 → Run 失败
       ├── 如果所有敌人死亡 → 战斗胜利
       └── 否则 → 回到玩家回合
```

## 9. 可扩展性设计

### 9.1 新增卡牌

**零代码流程**：
1. 在 `content/cards/{character}/` 新增 JSON 文件
2. 填写 Schema 定义（效果类型从已有枚举中选）
3. 更新内容版本号
4. 客户端下次启动自动同步

**需要代码的情况**：引入全新的效果类型（如"将手牌中所有攻击牌费用减 1"），需要在 `EffectResolver` 中注册新效果处理器。

### 9.2 新增角色

1. 在 `content/cards/{new_character}/` 添加角色专属卡牌
2. 在 `content/relics/` 添加角色起始遗物
3. 在角色定义中配置起始牌组、起始 HP、初始遗物
4. 在 `MapGenerator` 中注册角色可遇到的 Boss 池
5. 在服务端 `ProgressionService` 中添加解锁条件

### 9.3 多人模式扩展点

当前架构为单机设计，但预留了以下扩展点：

| 扩展点 | 当前设计 | 多人改造方向 |
|--------|---------|-------------|
| 通信协议 | REST（非实时） | 添加 WebSocket/SignalR 通道用于实时同步 |
| CombatState | 单玩家 + 多敌人 | 扩展为多玩家 + 多敌人，TurnManager 按玩家轮转 |
| EffectResolver | 单目标解析 | 添加友方目标选择、协作效果（如给队友加 buff） |
| RunState | 单人 run | 扩展为共享 run（共享地图、独立牌组、共享战斗） |
| ValidationService | 单人命令日志 | 扩展为多人命令日志交叉验证 |

**关键原则**：多人改造不需要重写 `game/` 逻辑层，只需要扩展数据结构和通信层。逻辑层的命令模式天然支持多人——每个玩家的操作都是独立的 Command。

## 11. 设计检查清单

### 11.1 架构检查清单

- [ ] 游戏逻辑层 (`game/`) 不依赖任何 UI 节点
- [ ] 所有 RNG 调用通过 `RNGManager`，不使用裸 `randi()`
- [ ] 所有玩家行动通过 Command 模式，有日志记录
- [ ] 内容定义使用 JSON，不硬编码在脚本中
- [ ] 客户端可完全离线运行一局完整 run
- [ ] 服务端可独立验证 run 合法性（不运行客户端逻辑）
- [ ] Autoload 之间无循环依赖
- [ ] 场景切换通过 `GameManager` 统一管理，不直接调用 `change_scene`

### 11.2 战斗系统检查清单

- [ ] 出牌到效果反馈延迟 < 1 帧
- [ ] EffectQueue 处理完一个效果后才处理下一个（避免竞态）
- [ ] 连锁效果（遗物触发）能正确追加到队列
- [ ] 敌人意图在玩家回合结束时计算（不是回合开始时）
- [ ] Retain 牌在手牌中正确保留
- [ ] Exhaust 牌进入消耗堆不回到弃牌堆
- [ ] 牌堆为空时自动重洗弃牌堆
- [ ] 战斗结束时 CommandLog 完整可回放

### 11.3 内容系统检查清单

- [ ] 每张卡牌有唯一 ID，不含特殊字符
- [ ] 每个效果类型在 EffectResolver 中有对应处理器
- [ ] 升级路径明确定义（数值变化或机制变化）
- [ ] 敌人 AI 行为可复现（相同 seed + turn → 相同意图）
- [ ] 内容版本号递增，客户端能检测并同步更新
- [ ] JSON Schema 校验在开发阶段自动执行
